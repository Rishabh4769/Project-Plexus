# SIEM Features for a Small Local Network-Monitoring Project (Plexus context)

## Summary

A SIEM is not a packet counter with prettier charts. Authoritative definitions converge on a pipeline: **collect logs/events from many sources → parse and normalize them to a common schema → store them centrally and searchably → run detection/correlation rules over them → alert with priority → let an analyst triage/investigate → report and retain the evidence.**

For the project in scope — Python + FastAPI + React, already doing live packet capture, traffic/port statistics, basic alerts and an HTML session report, solo beginner, 8 GB RAM, local-only — most of that pipeline is reachable in miniature **without** enterprise infrastructure, by re-using what already exists and adding: (1) persistent normalized storage in SQLite, (2) one or two host-log sources (auth/system logs) parsed into the same schema as packets, (3) a tiny declarative rule engine with threshold/time-window correlation, (4) an alert lifecycle (acknowledge/resolve/false-positive + notes), (5) search/filter + timeline investigation, (6) a static MITRE ATT&CK tag per rule, and (7) a single free blocklist check. That sequence, in that order, is the highest value-for-effort path to a genuine mini-SIEM.

Explicitly out of scope at this scale: Elasticsearch/OpenSearch, distributed agents, UEBA/ML, SOAR auto-response, cloud connectors, and 1-year enterprise retention — see §4. Resource proof: even Security Onion, the canonical open-source bundle, lists **24 GB RAM minimum for Standalone** (8 GB only for a stripped Eval node) — more than the whole laptop in scope.

Confidence: high for the core feature list (NIST SP 800-92 as summarised, CISA/ASD 2025 guidance, Wazuh official docs, TrustedSec all agree); medium for effort grades — they are engineering judgement applied to the stated stack/constraints, not a sourced fact.

## Findings

### 1. Core, must-have SIEM features

| # | Core feature | What it means in a real SIEM |
|---|---|---|
| 1 | **Log / event collection & ingestion** | Central collection from many source types — OS, network devices, firewalls, identity/auth, applications, cloud — via agents, syslog, or API pulls. NIST glossary defines SIEM as providing "centralized logging capabilities for a variety of log types"; SP 800-92's loop starts with a SIEM server receiving logs from log generators, analysing across sources, correlating, prioritising and initiating responses, and notes products support "several dozen types of log sources" [sazabi/NIST summary]. CISA/ASD's 2025 package adds a dedicated *Priority Logs for SIEM Ingestion* practitioner guide — ingestion should be prioritised, not indiscriminate, and the agencies "strongly discourage using a SIEM as the central repository for all logs" [CISA; Snare summary]. Wazuh collects from Linux/Windows/macOS endpoints, syslog devices, agentless SSH, cloud providers and custom apps, via agent, syslog or third-party APIs [Wazuh]. |
| 2 | **Log parsing & normalization** | Raw, vendor-specific text is parsed into structured fields and mapped to one schema (ECS, OCSF, CEF/LEEF, or a home-grown equivalent), so `src`, `sourceIPAddress` and `remote_addr` all become e.g. `source.ip`. ECS documentation makes the payoff concrete: without it a search must try `src:… OR client_ip:… OR src_ip:…`; with it, `source.ip:…` alone [Elastic ECS]. Wazuh calls these parsers *decoders*: "responsible for parsing and normalizing log data… converting raw log data in several formats into a unified and structured format," extracting timestamp, level, source IP, username [Wazuh]. TrustedSec lists "log ingestion, normalization, and custom fields" as requirement #1 [TrustedSec]. |
| 3 | **Centralized storage & search** | Parsed events/alerts are indexed and stored centrally so an analyst can query across sources and time, pivot on an IP/user/host, and reconstruct a timeline. Wazuh's indexer "stores and indexes alerts… as JSON documents" in `wazuh-alerts-*`, plus `wazuh-archives-*` for all events (disabled by default "because of the huge storage requirements") [Wazuh]. |
| 4 | **Correlation rules** | Linking events that are weak alone but strong together — e.g. many failed logins from one IP across services within a window, or a failure burst followed by a success. This is what separates a SIEM from a log collector: TrustedSec — "A differentiator between a log collector and a SIEM is the ability to correlate events and alert on positive matches using a rules engine… based on more than one event type" [TrustedSec]. Sigma, the vendor-neutral rule format, formalises this with selections + a `condition`, plus explicit rule-correlation documents for event counts/relationships across events [Sigma spec]. Wazuh rules can likewise count `frequency` within a `timeframe` and reference parent/matched rules [Wazuh via search index]. |
| 5 | **Detection rules & alerting** | A ruleset (built-in + custom) matched in/near real time, producing prioritised alerts. Wazuh ships 3,000+ rules; a rule has a match pattern, a `level` (priority) and generates an alert above a threshold (default 3) [Wazuh]. Sigma rules carry `level`, `title`, `logsource`, `detection` [Sigma spec]. |
| 6 | **Dashboards & visualization** | A "single pane of glass": trends, top talkers/alerts, failed logins over time, drill-down for triage. Wazuh dashboard provides predefined security/compliance dashboards, real-time filtering/drill-down by event/time, and custom dashboards [Wazuh]. TrustedSec: dashboards "can be created for different types of investigations where many queries can be run from a single place, rapidly speeding up triage" [TrustedSec]. |
| 7 | **Incident / alert management workflow** | Alerts are not fire-and-forget: they have severity, status, assignment/acknowledgement, notes, escalation to a case/incident, and closure. Security Onion illustrates the full form — its console has Alerts for triage and Cases to "escalate… document findings, attach evidence, and track the investigation through to closure," plus TheHive as case management [Security Onion via index]. This workflow layer is part of every mature SIEM/SOC description even where NIST/CISA describe it as triage/prioritisation rather than a named module. |
| 8 | **Reporting** | Scheduled/summary and compliance reports: counts, trends, top rules/sources, evidence for audits. Wazuh's ATT&CK module "generates reports and visualizations… frequency and severity" [Wazuh threat hunting]; TrustedSec lists a built-in scheduled reporting/analytics engine alongside dashboards [TrustedSec]. |
| 9 | **Retention** | A deliberate policy for how long events stay searchable/archived, then are deleted. 2025 CISA/ASD practitioner guidance (as quoted): "at a minimum, one year for logs that record administrative and security-related events, and 90 days for informational logs" for organisations starting out [Snare summary of CISA guidance]. Wazuh archives exist specifically to provide "log retention, indexing, and querying" for non-alerting events [Wazuh threat hunting]. |
| 10 | **Threat intelligence feeds** | External indicators of compromise (malicious IPs/domains/URLs/hashes) used to enrich/match events and raise detection confidence. TrustedSec lists "threat intelligence components or integration" as a basic SIEM requirement [TrustedSec]. Wazuh's server "leverages multiple threat intelligence sources and enriches alerts with contextual data" [Wazuh server, index]. Concrete free tier: abuse.ch URLhaus, Feodo Tracker (botnet C2 IPs), ThreatFox, MalwareBazaar — listed as free, no API key for several feeds; AbuseIPDB free tier 1,000 checks/day [Kyra MDR docs, index]. |
| 11 | **MITRE ATT&CK mapping** | Tagging detections/alerts with tactic (the adversary's *why*) and technique (the *how*, e.g. T1110 Brute Force, T1078 Valid Accounts) so alerts speak a shared language and coverage gaps are visible. MITRE: ATT&CK is a "knowledge base of adversarial techniques based on real-world observations," organised by tactics/techniques/sub-techniques/procedures [MITRE]. Wazuh rules literally embed `<mitre><id>T1110</id></mitre>` and its dashboard module maps TTPs to events with frequency/severity views [Wazuh]. Sigma rules do the same via `tags: attack.t1110` [Sigma spec]. |

Adjacent, often bundled but **not core SIEM** in the sources above: file-integrity monitoring, vulnerability scanning, security configuration assessment (Wazuh extras), and SOAR automated response (CISA treats SIEM and SOAR as separate platforms, SIEM first).

### 2. Feasibility grading for this project

Grades: **(a) easy small change** = days, existing stack only · **(b) medium** = a focused feature, 1–3 weeks of beginner work / a new subsystem done simply · **(c) enterprise-scale / out of scope** = needs infrastructure, scale, or expertise the constraints exclude. Where a feature splits, both grades are given.

| Feature | Grade | One-line reason |
|---|---|---|
| 1. Collection — packets (already have) + **1–2 local log files** (Linux `auth.log`/`journalctl`, or Windows Event export) | **(a)** | Tail/read a local file in Python and emit events — no agent network needed. |
| 1b. Collection — multi-host agents, syslog fleet, cloud/API connectors | **(c)** | Agent lifecycle, transport security and dozens of parsers are Wazuh's whole product. |
| 2. Parsing & normalization to a **small** common schema (~12–15 fields: timestamp, source_type, src_ip, dst_ip, src/dst port, protocol, user, action, outcome, severity, raw) | **(a)–(b)** | A dataclass/dict + 2–3 regex parsers (packets already structured; sshd/sudo lines are regular) — borrow ECS field names, don't implement ECS. |
| 3. Centralized storage & search — **SQLite** (stdlib) + indexed columns / FTS for message, filtered search API + React page | **(a)–(b)** | SQLite is embedded in FastAPI's process, zero extra RAM/service; Elasticsearch is the (c) version (see §4). |
| 4. Correlation — **threshold/time-window rules only** (e.g. ≥5 failed logins or ≥20 distinct ports from one IP in 5 min → alert; failure-burst → success) | **(b)** | A sliding-window counter keyed by IP/user over stored events is ~100 lines; general cross-source graph/stateful correlation is (c). |
| 5. Detection rules & alerting — declarative YAML/JSON rules evaluated per event | **(a)–(b)** | Project already raises basic alerts; making them data-driven (field, operator, value, severity) is a refactor, not a new platform — Sigma-*inspired*, not Sigma-converted. |
| 6. Dashboards & visualization | **(a)** | Already has a React dashboard with traffic/port stats; adding alert counts by severity/rule/ATT&CK and a time series reuses existing charting. |
| 7. Alert management workflow (open → acknowledged → resolved / false-positive, + notes, severity) | **(a)** | One `status` + `notes` column, one PATCH endpoint, one Alerts page — highest workflow payoff per line of code in the list. |
| 8. Reporting | **(a)** | Already generates an HTML session report; extend it with alert/rule/ATT&CK summaries from the DB instead of only packet stats. |
| 9. Retention — configurable days (e.g. 7–30) + scheduled prune / export to JSONL/CSV and delete | **(a)** for the mechanism; **(c)** for enterprise 1-year retention | A nightly `DELETE WHERE timestamp < …` is trivial; storing/searching a year of events on a laptop is not the goal (guidance target is for organisations, see §1.9). |
| 10. Threat intel — **one static blocklist** (e.g. Feodo Tracker C2 IP list / URLhaus recent CSV), downloaded periodically, matched on dst_ip | **(a)–(b)** | It's a text/CSV download + a set lookup at alert time; a full TI platform (STIX/TAXII, MISP, scoring, multiple feeds) is (c). Note current abuse.ch access terms/auth should be re-checked at implementation time — sources disagree on whether a free auth key is now required for some endpoints. |
| 11. MITRE ATT&CK mapping — static tag on each rule | **(a)** | Just a string field per rule (e.g. port scan → T1046 Network Service Discovery, brute force → T1110, valid-account success after failures → T1078) displayed/filtered in UI; a full ATT&CK coverage matrix/Navigator is (b)–(c) and low value with ~8 rules. |

### 3. Highest-value small additions — ordered by value-for-effort

1. **Persist normalized events in SQLite (the foundation).** *What:* an `events` table with the ~15-field common schema in §2.2; packet capture writes rows in that shape instead of/in addition to in-memory stats. *Why it matters:* without stored, uniform events there is no search, correlation, retention or SIEM claim at all — every later item depends on it. *Technically:* Python stdlib `sqlite3` (or existing stack), indexes on timestamp/src_ip/dst_ip, a `/events?src_ip=&from=&to=&type=` FastAPI endpoint. No new service, negligible RAM.
2. **Alert lifecycle + Alerts page.** *What:* alerts become DB rows with severity, rule name, status (open/acknowledged/resolved/false-positive), notes, first/last seen, count. *Why:* this is the visible difference between a monitor that beeps and a SIEM an analyst works in — triage workflow is core feature #7. *Technically:* one table, PATCH status endpoint, one React page reusing existing alert data.
3. **Ingest one host log source into the same schema — auth logs first.** *What:* tail Linux `/var/log/auth.log` (or `journalctl -u ssh --output=json`) and parse sshd/sudo success/failure lines into events with user, src_ip, outcome; on Windows, the equivalent single source is Security event log export. *Why:* CISA's *Priority Logs* guidance prioritises identity/authentication logs, and this is the first step from "network monitor" to multi-source SIEM — it also unlocks real correlation (network + host). *Technically:* a file-tail loop + 3–4 regexes; keep the raw line in a `raw` field so parser bugs aren't data loss.
4. **Simple declarative rule engine.** *What:* rules in a YAML/JSON file — match fields + optional threshold (`count ≥ N within M seconds, group by src_ip/user`) → create alert with severity + ATT&CK tag. Ship ~6–8 rules: port scan, failed-login burst, failure-burst-then-success, connection to blocklisted IP (see #6), new listening/unusual port, high-volume outbound to a single host. *Why:* detection + correlation (features #4–5) are the SIEM differentiator over a log collector [TrustedSec]. *Technically:* evaluate single-event rules on ingest; evaluate threshold rules with an in-memory/deque or SQL window query per key — deliberately no streaming framework.
5. **Event search & timeline investigation page.** *What:* filterable event list (IP, user, type, time range, outcome) + clicking an IP/user shows all its events across packets *and* auth logs in time order. *Why:* investigation/pivot is what storage is for; it makes demos and real home-lab incidents answerable ("what did this IP do before the alert?"). *Technically:* the endpoint from #1 + a React table/timeline; SQLite FTS only if free-text search over `raw` is wanted.
6. **One threat-intel blocklist check.** *What:* periodically download one plain-text/CSV C2/malicious-IP list (Feodo Tracker is the textbook example in the sources), store as a set/table, flag any event whose dst_ip matches, enriching the alert with the feed name. *Why:* cheapest possible real enrichment — turns a generic "connection out" into "connection to a known botnet C2." *Technically:* `requests` GET on a timer/manual refresh button, set lookup in the rule engine (#4). Verify the feed's current access/auth terms before coding — see §2.10 caveat.
7. **MITRE ATT&CK tags + a tiny coverage view.** *What:* each rule carries one tactic/technique ID + name; alert detail links to its attack.mitre.org page; dashboard shows counts by technique. *Why:* near-zero cost, immediately makes the project read as a SIEM to assessors/employers and teaches the shared vocabulary Wazuh/Sigma use natively. *Technically:* two string columns + a static dict of the ~8 techniques used; do **not** build a matrix.
8. **Retention prune + report upgrade (tie-off).** *What:* settings for retention days (default e.g. 14), a prune job, and extending the existing HTML report with top alerts/rules/ATT&CK techniques, acknowledged vs unresolved alerts, and blocklist hits. *Why:* closes the loop on features #8–9 and prevents SQLite from eating the laptop disk — a real failure mode for packet tools. *Technically:* a scheduled `DELETE`/vacuum-lite + report queries that are mostly the dashboard queries reused.

Deliberate sequencing note: #1–#2 should land first — they convert existing behaviour to SIEM shape for almost no risk. #3–#4 are where it *becomes* a mini-SIEM. #5–#8 are polish with high demo/learning value.

### 4. What NOT to attempt at this scale — and why

- **Elasticsearch / OpenSearch / the ELK stack (and therefore running Wazuh or Security Onion itself as the base).** Security Onion 2.4 docs: Standalone minimum **24 GB RAM, 4 cores, 200 GB**; Manager/Search nodes 16 GB; even Eval (which disables Logstash/Redis to save RAM) is 8 GB for the node alone [Security Onion hardware]. On an 8 GB laptop that also runs the OS, browser and dev tools, this crowds out the project itself. SQLite answers the same queries at home-lab volume.
- **Distributed multi-host agents / fleet management.** Enrollment, agent updates, encrypted transport, heartbeat/health (Wazuh's `wazuh-monitoring` etc.) is a product in itself; local files + optionally one syslog listener give 90% of the learning value.
- **UEBA, ML/anomaly baselining, behavioural analytics.** Needs weeks of clean baseline data, tuning, and statistics beyond beginner scope, and produces unexplainable false positives at tiny data volumes. Threshold rules are explainable and testable.
- **SOAR / automated response** (auto-blocking IPs in the firewall, killing processes, isolating hosts). CISA's guidance treats SOAR as a separate platform to adopt *after* a SIEM is properly implemented, and notes it is usually unsuitable for immature environments [CISA package via index summaries]. Auto-blocking on a home network from a beginner rule engine is also the fastest way to lock yourself out.
- **Cloud connectors, compliance packs (PCI/HIPAA/GDPR mapping), and 1-year hot retention.** No cloud/no compliance obligation in scope; the 1-year figure is organisational guidance, not a student-project requirement. Export-and-prune beats pretend-compliance.
- **Full Sigma conversion, STIX/TAXII/MISP threat-intel platform, Kafka/stream processing, multi-tenancy/RBAC/SSO.** Each is an enterprise integration surface. Borrow their *ideas* (Sigma-style rule fields, ATT&CK tags, one flat blocklist) without importing their infrastructure.
- **Trying to ingest everything.** Directly contrary to CISA/ASD advice to prioritise specific security logs over "logging for the sake of logging" — at laptop scale, volume is the enemy of signal and disk.

## Could not verify / open questions

- NIST SP 800-92 full text was relied on via a secondary glossary summary, not opened directly as a NIST PDF in this run; the definition/loop attributed to it is consistent across multiple independent summaries found, but a direct NIST citation should be added if the report is used academically.
- abuse.ch feed access terms: sources found disagree/changed over time on whether some abuse.ch APIs now need a free auth key vs no key. Flagged in §2.10 — must be re-checked live at implementation time; do not hard-code an assumption.
- Effort grades and the 6–8 rule list are judgement for the stated stack, not sourced benchmarks; actual effort depends on the project's current alert/storage code, which was not inspected.
- OSSIM was named in the mission but no primary OSSIM source was opened; its feature set (asset discovery, IDS correlation, SIEM) is subsumed by the Wazuh/Security Onion evidence and adds nothing to the grading, so it was not pursued further.
