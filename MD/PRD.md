# PRD: ML-Based Intrusion Detection Integration for PLEXUS

**Version:** 0.2 (Draft — Planning Stage)
**Author:** Rishabh

**Last updated:** 2026-07-14

## 1. Overview

PLEXUS is an existing network traffic monitor: **FastAPI + Scapy backend**, **React frontend**, SQLite storage, token-based auth, and a live WebSocket stream. It already does live packet capture, session history, PDF reporting, and **rule-based** anomaly alerts (port-scan and traffic-flood thresholds, hardcoded in `sniffer.py`).

This PRD covers replacing/augmenting those hardcoded thresholds with a **trained ML classifier** that flags malicious traffic — a real NIDS component — using **CICIDS2017** and a Random Forest / XGBoost model.

Dual purpose:
- **Course deliverable** — small, defensible model (reduced feature set, 2 days of data) for submission.
- **Portfolio piece** — end-to-end systems thinking: capture → feature engineering → inference → alerting, alongside PLEXUS itself and Veronica as flagship projects.

## 2. Problem Statement

PLEXUS currently flags "Port Scanning" and "Flooding" using two hand-picked thresholds (`max_ports_scanned`, `max_packets_flood`) inside `PacketSniffer._packet_callback`. This catches only the two attack shapes someone explicitly coded for, with no notion of "normal" vs. "abnormal" learned from real data. The goal is to add a trained model that classifies traffic more generally, without throwing away the existing alert pipeline — reuse it.

## 3. Goals

| Goal | Description |
|---|---|
| G1 | Clean CICIDS2017 (Monday + one attack day), select ~15-20 features via Random Forest importance, train RF/XGBoost |
| G2 | Build a flow-aggregation layer that turns PLEXUS's live packet stream into the same feature shape the model expects |
| G3 | Wire model predictions into the **existing** `alert_queue` → `alerts` table → `AlertTable.jsx`/WebSocket pipeline — no new schema, no new UI surface needed for v1 |
| G4 | Support batch inference on an uploaded/selected PCAP, reusing the same feature pipeline |
| G5 | Document dataset, feature selection method, and metrics for the course submission |

## 4. Non-Goals (Out of Scope for v1)

- Deep learning models (RF/XGBoost only)
- Multi-class attack typing (binary Normal/Attack only — CICIDS2017 subtype labels are a stretch goal)
- Removing the existing rule-based alerts — they stay as a cheap first line; the model is additive
- Full 78-feature / all-8-days CICIDS2017 model (that's the later "full access" phase, once course version ships)
- Inline blocking/prevention — detection only

## 7. Dataset & Feature Plan

- **Dataset:** CICIDS2017 (not NSL-KDD — pivoted because CICIDS2017's flow-level features, generated by CICFlowMeter, map much more directly onto live packet-stream aggregation than NSL-KDD's older format).
- **Scope for v1:** Monday (benign baseline) + Friday PM (DDoS or PortScan) — most separable attack pattern, keeps the first working model simple. Wednesday/Thursday (multi-attack-type days) deferred to the "full" model phase.
- **Cleaning required:** drop identifier columns (Flow ID, Source/Destination IP, Timestamp, Source Port — these cause leakage/memorization, not learning); drop zero-variance columns; handle `Infinity`/`NaN` in `Flow Bytes/s` / `Flow Packets/s` (divide-by-zero on 0-duration flows); check for duplicate rows; check label balance (CICIDS2017 skews heavily benign, so F1/recall matter more than raw accuracy).
- **Feature reduction:** train one throwaway RF on all cleaned columns, take feature-importance ranking, keep top 15-20. This is an empirical cut, not a hand-picked one — needed for the "small model" requirement without guessing which features matter.

## 8. Proposed Solution

### 8.1 Model Training Pipeline (offline)
1. Load Monday + chosen Friday PM CSV, clean per §7.
2. Encode/scale as needed, binary label (Benign / Attack).
3. Train RF and XGBoost, compare via cross-validation.
4. Rank features by importance, cut to top 15-20, retrain on reduced set.
5. Evaluate: F1, precision, recall, confusion matrix.
6. Serialize model + scaler/encoder together (`joblib`) — inference breaks if these drift apart.

### 8.2 The Core Technical Challenge: Feature Mapping
CICIDS2017 features are flow-level (duration, packet/byte counts, IAT stats, flag counts) computed by CICFlowMeter — not raw Scapy packet fields. `PacketSniffer` already tracks *some* per-source-IP state (`self._connections`, `self._packet_counts`) for its rule-based alerts — this is a starting point, but it needs to become a proper 5-tuple flow tracker (src IP, dst IP, src port, dst port, protocol) computing the same ~15-20 stats the model was trained on, over a sliding time window.

This flow-aggregation module is the single biggest new piece of engineering — bigger than training the model — and should reuse/extend the connection-tracking already in `sniffer.py` rather than being built from scratch alongside it.

### 8.3 Real-Time Inference Path
```
Scapy sniff loop (existing _packet_callback)
  → flow aggregator (extends existing self._connections tracking)
  → feature vector (matches trained model's reduced feature set)
  → model.predict()
  → alert_queue.put(...)              # SAME queue rule-based alerts already use
  → database.py: log_alert()          # SAME table, no schema change
  → /ws/stream                        # SAME websocket, no new endpoint
  → AlertTable.jsx                    # SAME component, no new UI needed for v1
```

### 8.4 Batch Inference Path
```
Upload/select PCAP → Scapy rdpcap → same flow aggregator (applied to full file)
→ feature vectors → model.predict() (batch) → results
→ reuse existing session/report structure, or a simple new endpoint returning a summary
```

### 8.5 Backend Changes
- New `ml/` package (training + inference), imported by `backend/sniffer.py` and one new route in `backend/main.py` for batch analysis.
- No new SQLite tables required for v1 — model-flagged alerts go through the existing `alerts` table. Optionally add a `source` column (`"rule"` vs `"model"`) later to distinguish them; not required to ship.

### 8.6 UI Changes
- **None required for v1** — model alerts flow through the existing `AlertTable.jsx` + WebSocket pipeline automatically once the backend emits them.
- Optional stretch: a small badge on `AlertTable` distinguishing rule-based vs. model-based alerts, once the `source` column above exists.

## 11. Risks

| Risk | Mitigation |
|---|---|
| Flow aggregator doesn't reproduce CICFlowMeter's exact stats | Validate against a small labeled CICIDS2017 PCAP before wiring into live capture (M3) |
| Class imbalance (mostly benign) inflates accuracy, hides poor recall | Evaluate with F1/recall/confusion matrix, not accuracy alone |
| Real-time latency / dropped packets under load | Prove batch mode first (M4) before real-time (M5) |
| Scope creep — trying all 8 days or multi-class too early | Locked to 2 days, binary, ~15-20 features for v1; explicitly deferred in §4 |
